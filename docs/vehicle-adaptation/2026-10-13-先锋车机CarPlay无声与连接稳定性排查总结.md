# 先锋车机 CarPlay 无声与连接稳定性排查总结

日期：2026-10-13。本文记录本次实际定位、修改、部署和验证过程。时间均采用车机日志中的本地时间。

## 一、关键结论

1. **CarPlay 无声的主要问题位于先锋车机的音频输出和音源控制层。**现场已经收到音频包，完成解密，并将媒体 AAC、导航 Opus 解码为 PCM。因此，本次主要无声问题不能归因于 iPhone 未发送音频或音频 UDP 完全被防火墙阻断。
2. **这台车机需要厂商扩展音频通道和音源令牌。**普通 Android 的 `USAGE_MEDIA`、导航 usage，不能替代先锋的媒体流 `401` 和导航流 `400`。媒体最终进入前排 `FRONT` 输出，导航进入 `MIX` 混音输出。
3. **播放通道、音源选择、音频焦点是三个需要分别处理的环节。**正确创建音轨后，若主音源仍停留在蓝牙或 FM，CarPlay 音乐依然可能没有对应声音出口。实机确认选择前排媒体音源的正确调用为 `MediaController.change2Source(1, 300)`。
4. **媒体和导航必须分别持有焦点。**首版适配暴露了一个二次问题：共用焦点管理器在导航开始时先释放媒体焦点，先锋随后关闭主音源。最终版保留媒体焦点，并为导航、助手语音单独管理混音焦点，播报结束只释放混音焦点。
5. **旧版还存在音频写入长期阻塞的问题。**普通输出线程停在底层 HAL 写入，播放队列随后堆满。最终版在识别出的先锋固件上使用非阻塞写入，对连续无进展设置有限等待，使播放器能响应退出，减少旧播放资源积累。
6. **源码修复已构建并覆盖安装到车机。**31 项定向检查通过；媒体和导航播放进度持续增长；本机 QQ 音乐被暂停以避免两路音乐叠加；两次主动重连成功，保存的最终版短时会话日志未出现自行断线。
7. **尚不能认定所有无线掉线问题都已解决。**本次确认并修复的是音频适配、焦点生命周期和播放线程阻塞问题。初始握手曾出现一次 `peer EOF`，其具体原因未完全定位；长期无线稳定性、物理 MODE 键完整行为及实际车内听感仍未完成工具层面的验证。

**关于 FM 测试的补充：**采样中曾先看到 FM 音源 `201`，后又看到媒体音源 `300`。你随后说明，这可能是你手动切换回媒体。因此，本文不把这一变化认定为程序自动回切缺陷，也不据此推导新的根因。能够确认的是，某次采样同时出现 `source=201` 与 `mix=400`，证明 FM 主音源与 CarPlay 导航混音可以并存。

## 二、问题背景与本次范围

原始现象是：车机已经能连接并显示 CarPlay，但没有声音；车机实际使用中需要通过方向盘 MODE 键在车载音乐、媒体、蓝牙和 FM 等音源之间切换。原有导航应用能够出声，而 CarPlay 连接后媒体、导航声音不正常。另外，CarPlay 曾经频繁断开。

本次按你的要求，参考以下工作区的播放实现和已有分析资料：

- `/Users/zhouhao/work/project/车载软件/amap`
- `/Users/zhouhao/work/project/车载软件/qqmusic`

同时查看了与车机实际音乐平台相关的 `wecarflow` 工程及已有先锋固件分析材料。参考工程用于寻找差异，最终通道参数和调用方式以车机实际框架、系统音轨和实机实验为依据。

本次修改的是 DiPlay 源码，并通过 `adb install -r` 覆盖安装。没有修改高德或 QQ 音乐 APK，没有 root 车机，没有修改防火墙、路由或系统音频服务，也没有通过重启系统服务清除旧音轨。

Mac 上启动了 `caffeinate -di`，用于阻止空闲休眠和显示器空闲息屏；在本次验证结束及整理文档时均检查到该进程仍在运行。

## 四、定位方法：先确认声音在哪一层停止

本次没有直接把“没有声音”当作音量设置问题，而是分层收集证据：

| 层次 | 检查内容 | 判断目的 |
| --- | --- | --- |
| CarPlay 会话 | SETUP、会话激活、视频帧、iAP 控制消息 | 确认已进入真实运行会话 |
| 网络音频 | 音频流协商、RTP 接收数量、解密情况 | 区分网络收不到与下游播放失败 |
| 解码 | AAC / Opus 格式、PCM 输出、解码计数 | 确认编码格式是否能处理 |
| Android 音轨 | AudioTrack 状态、写入、播放头、队列 | 判断数据是否真正被音轨消费 |
| 系统音频 | AudioFlinger 输出线程、音轨所在总线、写入帧数 | 判断是否进入正确硬件输出路径 |
| 先锋音源 | 当前 Source ID、MainToken、MixToken、焦点返回值 | 判断车机当前允许哪一路声音输出 |

主要使用的证据包括 DiPlay 会话日志、车机 `logcat`、`dumpsys audio`、`dumpsys media.audio_flinger`、`dumpsys media.audio_policy`、MediaManager 状态、媒体会话状态以及车机实际框架中的常量和方法。

## 五、第一步：排除“没有音频数据”的假设

现场日志显示，车机已经接受音频流，例如媒体流 `type=102` 和导航流 `type=101`。音频 UDP 数据口使用了既有固定端口方案中的 `9911` 或 `5656`。

随后可以观察到：

- 音频接收统计持续增长。
- 媒体格式为 AAC-LC，48 kHz、双声道。
- 导航格式为 Opus，48 kHz、单声道。
- 解码器报告输出格式，媒体已出现 PCM 解码输出。
- 播放队列出现 `Audio: queue full`。

这些证据把主要故障范围收敛到了解码后的播放端。尤其是“队列堆满”，说明上游仍在送数据，而下游无法正常消费。

需要注意：这些结论针对本次已经观察到的媒体和导航流，不代表所有音频流类型、所有并发组合或所有网络场景都已验证。

## 六、第二步：发现普通 Android 输出被卡住

AudioFlinger 的旧版快照中，普通 `SPEAKER` 输出线程 `AudioOut_D` 出现以下异常：

```text
Output device: SPEAKER
Blocked in write: yes
Frames written: 4608
```

该线程的写入帧数长期没有正常增长，多条音轨仍显示活动，但服务器侧播放进度停滞。与此对应，DiPlay 的媒体、导航队列持续积压。

这说明，仅看到 `AudioTrack.STATE_INITIALIZED` 或调用了 `play()`，不足以认定声音已经输出。必须继续观察播放头、输出线程和硬件消费进度。

旧实现使用 `AudioTrack.WRITE_BLOCKING`。当先锋把某个输出路径停在底层写入时，播放工作线程可能长期无法从该调用返回，线程中断和退出标志无法及时被处理。后续流替换、会话退出或重连就容易留下尚未释放的播放资源。

本次确认了这种阻塞和旧轨道积累现象，但没有证明它是此前每一次无线断开的直接原因。

## 七、第三步：对照高德、QQ 音乐与实际固件

### 7.1 为什么要比较正常播放的应用

高德能在其它主音源下播报，说明车机存在独立导航混音路径；车载 QQ 音乐能播放，说明车机的媒体输出也有已知可用路径。这两类正常行为分别提供了导航和媒体的参考。

高德工作区中的音轨工厂、音频配置和焦点管理代码，体现了按渠道配置创建音轨、请求焦点的结构。QQ 音乐工作区中既有标准 Android 播放实现，也有车机 PAL 平台接入材料。不能把某个通用 SDK 内的 `STREAM_MUSIC=3` 调用，直接当作这台先锋车机的最终实现。

实机上，车载音乐平台进程是 `com.tencent.wecarflow`。它的音轨进入 `FRONT` 输出，AudioFlinger 中实际类型为 `11`，与 DiPlay 原先进入普通输出的路径不同。

### 7.2 读取实际框架确定厂商扩展

进一步读取车机框架，检查 `AudioManager`、`AudioAttributes`、`AudioTrack`、`AudioSystem` 和先锋 MediaController 的接口与常量，确认以下映射：

| 概念 | 媒体 | 导航 |
| --- | --- | --- |
| 厂商 streamType | `401` | `400` |
| AudioManager 常量 | `STREAM_TAI_WECARFLOW_MEDIA` | `STREAM_AMAP_NAVI_GUIDE` |
| 厂商 contentType | `401` | `400` |
| 最终音频总线 | FRONT | MIX |
| 底层 legacy 类型 | `11` | `10` |
| 音源令牌 | `com.tencent.wecarflow.media` | `com.autonavi.amapauto` |

先锋扩展了 `AudioAttributes.Builder.setLegacyStreamType()`，可识别 400、401 等厂商类型。AudioTrack 构造时根据 contentType 生成令牌，并通过厂商接口设置到音轨。

因此，通道、令牌和音源管理需要配套使用，普通 usage 不能提供相同含义。

这里必须区分三个数字空间：

- CarPlay 协议音频流类型，如 `100`、`101`、`102`。
- 先锋厂商 Android 音频流类型，如 `400`、`401`。
- 先锋系统音源编号，如 FM `201`、蓝牙 `205`、媒体 `300`。

这三类编号不能互换；例如 CarPlay 媒体 `type=102` 并不意味着使用 Android streamType 102。

框架分析中部分方法包含优化后的字节码，无法完整反编译。结论只采用明确可读的常量、方法签名、映射代码和实机行为；反编译器生成的失败占位代码不视为实车实现。

## 八、首版修复：接通正确音轨和厂商焦点

新增 `PioneerAudioRouting.kt`，限定在同时满足下列条件时启用：

- Android API 为 25。
- 框架存在媒体流 401 和导航流 400 的厂商常量，且值匹配。
- AudioTrack 存在厂商 `setTokenName(String)` 方法。

这样可以把适配限制在已识别的固件能力上，避免将厂商流类型硬套到普通 Android 设备。

默认媒体使用 401，导航和其它被映射到该兼容语音路径的音频使用 400；用户明确指定的媒体、导航音频通道仍优先。语音路径适配不等于已完成 Siri 和实际电话通话的全部验证。

同时修改 Android 7 的焦点兼容层，增加可选的原始 streamType。旧兼容层只根据 usage 推导标准流，可能把厂商类型折叠成 `STREAM_MUSIC=3`；现在先锋请求保留 400 / 401，普通设备继续沿用原有推导逻辑。

在这台先锋固件上，厂商焦点承担输出路径激活作用，因此即使通用音频焦点设置处于默认关闭状态，也会对识别出的厂商路径请求对应焦点。这是设备适配的实际行为，需要与通用设置含义区分。

首版安装后，媒体和导航的 `playbackHeadFrames` 都开始增长，证明此前播放端不消费 PCM 的主要问题已经被突破。

## 九、第四步：发现“正确音轨”还不等于“正确主音源”

首版音轨能够消费 PCM，但系统主音源仍是蓝牙：

```text
Current Source ID = 205
MainToken = mediamanager.source.name.bt-audio
```

此时媒体焦点请求曾返回 `granted=0`，而导航混音焦点可以返回 `granted=1`。这表明主音源控制与音轨创建是独立问题，不能只凭播放头增长判断媒体扬声器出口已经被选中。

检查 MediaController 常量和 Binder 接口，并做小范围实机调用，确认：

```text
DISPLAY_ID_FRONT = 1
SOURCE_ID_TAI_AUDIO = 300
change2Source(1, 300)
```

参数含义是“前排显示 / 控制域、目标音源”，不是“目标音源、切换原因”。早期参数顺序不正确的实验返回 `-1`；正确调用返回 `0`，当前音源变为 300，MainToken 变为 `com.tencent.wecarflow.media`。

最终实现通过反射调用车机现有 MediaController，在媒体轨道取得播放权时检查当前音源，必要时选择 300。它没有在每个 RTP 包到达时重复切换音源。

## 十、第五步：处理本机音乐与 CarPlay 音乐叠加

音源 300 同时是本机车载音乐平台使用的音源。实际切换后，系统可能启动或继续本机 QQ 音乐，AudioFlinger 中一度同时存在本机播放器和 DiPlay 的前排活动音轨。

这时即使 CarPlay 出声，也可能听到两路音乐。

检查本机 `com.tencent.wecarflow` 导出的 `MediaButtonIntentReceiver`，确认它支持明确的 `KEYCODE_MEDIA_PAUSE`。最终版在媒体轨道激活后延迟 500ms，向这个确定的接收器发送暂停事件。

延迟回调先检查该媒体轨道仍然有效、协调器尚未关闭，避免旧轨道的回调在退出后继续操作本机播放器。

实机媒体会话验证显示：

- 本机 QQ 音乐为 `PlaybackState state=2`，即暂停。
- CarPlay 媒体播放时为 `state=3`。
- 主音源保持为车载媒体。

这个广播只发给本机指定音乐应用，不是向其它设备或人员发送消息，也没有修改本机 QQ 音乐程序。

## 十一、第六步：修复导航播报导致主音源关闭的问题

首版适配中，原有焦点协调器仍把媒体和导航作为一个共享焦点请求处理。导航开始时，它会放弃原媒体请求，再申请导航请求。

在普通 Android 上，这可以被理解为焦点所有权更新；在这台先锋上，放弃媒体流 401 的焦点还会影响底层主音源状态。实机曾观察到：

```text
Current Source ID = 0
Current Mix ID = 400
MainToken = mediamanager.name.invalid
MixToken = com.autonavi.amapauto
```

也就是说，导航混音存在，但主音源已经被关闭。这解释了为什么首版可能出现“音轨能播放，音乐却在导航播报后再次静音”的二次故障。

最终方案改为两个独立生命周期：

```text
媒体开始：选择媒体音源 → 持有 401 媒体焦点
语音开始：保留媒体焦点 → 另外持有 400 混音焦点
语音结束：只释放混音焦点，媒体继续
媒体结束：释放媒体焦点
```

导航和助手等使用 400 的语音轨道，共用一个独立混音请求，并通过轨道集合管理生命周期。只有最后一个语音轨道结束时，才释放该请求，避免一个语音流结束时影响另一个尚在运行的流。

增加的回归用例验证了：导航或助手开始不会先放弃媒体焦点；结束一条语音轨道不会提前释放另一条语音仍使用的焦点；媒体焦点一直保持到媒体停止。

最终版实机经过多次导航播报，主音源仍保持为媒体 300，媒体播放进度持续增长，没有再观察到上述“导航切换关闭主音源”的情况。

## 十二、第七步：让播放写入能够退出

针对识别出的先锋固件，PCM 写入从阻塞方式改为 `WRITE_NON_BLOCKING`。

当一次写入没有进展时，线程短暂等待 5ms 后重试；连续无进展达到 250ms 时结束当前写入循环。成功写入后重置连续停滞计时。因此，250ms 限制针对的是连续无进展，并不是一段 PCM 的整体播放时长上限。

这种处理的目的，是避免音源不可用或底层不消费时，播放线程永久停在 native 写入中。它也使线程中断、停止标志和资源释放有机会得到处理。

代价是：路径长期不消费数据时，当前未写完的 PCM 可能被舍弃。该处理保证退出能力，不能替代正确音频路由，也不能作为正常播放中的无损缓冲机制。

其它设备继续使用原有阻塞写入。最终正常播放窗口中，观察到媒体、导航播放头增长，且保存的末段统计为 `dropped=0`、`writeErrors=0`。

两次主动重连之间的 AudioFlinger 快照没有留下刚退出的新版 DiPlay 的前排音轨。这个检查验证了本轮停止 / 重启过程的资源状态；它不等同于覆盖所有自然断线和所有退出方式。

本轮开始前，旧版已在普通 SPEAKER 输出中积累的轨道仍然存在。由于没有重启系统音频服务，这些历史轨道没有在本次被清除；不应把它们计作新版重新产生的轨道。

## 十三、连接稳定性是如何分析的

### 13.1 先区分不同的“断开”

本次分别观察代理蓝牙状态、AirPlay 控制连接、屏幕和 iAP 隧道，以及应用是否被主动停止或覆盖安装。

本轮有明确证据的一次异常，是早期握手阶段出现：

```text
06:53:25  airplay control closing reason=peer EOF activeStreams=[]
```

当时尚无活动流，现有机制在约 2 秒后开始重试，后续成功进入 CarPlay 会话。该次 EOF 的具体触发原因没有完全定位，本次没有根据单条日志盲目调整协议超时或重连参数。

另外，代理端蓝牙 / RFCOMM 在 AirPlay iAP 隧道建立后结束，可能属于控制链路移交。判断是否发生 CarPlay 故障，必须同时查看车机侧会话、画面、控制消息是否继续，不能只看代理日志中的 `DISCONNECTED` 或 `SESSION_ENDED`。

### 13.2 本次改善了什么

本次修复了已确认的播放线程阻塞和焦点释放问题，这有助于避免流替换、停止和重连时积累播放资源。没有新增一套无线重连算法，也没有证明音频阻塞解释了此前全部无线断线。

最终验证采用了两次主动停止 DiPlay 再启动的方式。两次都重新建立会话，后续音频路径恢复；保存的各段最终版观察日志没有出现自行断线关闭记录。
