# 先锋有线 CarPlay：重连失败与卡顿分析

更新日期：2026-10-14。分析依据是车机实际日志和当前代码，车主下车前已将报告完整保存到 Mac。

## 目前可以确定什么

**这台车机曾经通过 USB 显示 CarPlay，但目前不能稳定重连。** 首次成功证明 lwIP 路线可行，不能因此认为连接稳定性已经解决。

**最新版这次失败的位置，是车机向 iPhone 发送 USB 网络数据持续超时。** 手机信任、配对和 MFi 认证都已通过；原来的“接口 3 无法接管”没有在这轮复现。现在需要解决的是 USB 网络通道的重连恢复，不能把全部剩余问题都归为画面处理或 VPN。

这条路线不创建系统 VPN 隧道，因此这次失败不需要再次通过 ADB 授予 VPN 权限来解决。

发送失败的关键日志是：`NCM_TX transferred=-110 ... endpoint=0x6`。这里的 `-110` 表示本次 native USB 调用超时。这能确定发送操作没有完成，**不能仅凭这一行就断言是坏线、iPhone 拒收、车机 USB 控制器故障，或某一种具体 USB 握手状态**。

收到了网络包，也收到了手机的邻居查询，说明本轮不是一开始就完全失去 USB 连接。APP 已生成回应，但回应没有成功写出，因此手机尚未建立后续 TCP 连接。此时继续修改 AirPlay 端口、VPN 权限或视频解码器，不能直接修复这个发送卡点。

## 为什么首次能连上，重连却不稳定

历史日志显示不是所有失败都属于同一个原因。

第一类是旧连接残留数据干扰新握手。旧版重连报过 `Invalid USBMUX frame length`；最新版在握手前清掉约 115KB 残留数据，本轮成功完成配对和认证，没有复现这个报错。清理措施帮助本轮越过了这个环节，仍需更多重连确认稳定性。

第二类是 USB 网络发送恢复不及时，甚至一直不恢复。首次成功版在短暂发送失败后，出现 `transferred=114 expected=114`，紧接着手机建立 TCP 连接。部分旧版重连也曾在约十秒后恢复发送，但后续仍未顺利显示画面。本轮则一直没有发送成功。

第三类是已经重新显示画面，又很快断开。18:07:56 的历史记录有首帧，18:08:09 首先记录事件连接关闭，随后控制及画面连接关闭、重新启动。仅凭现有记录，无法确定最先关闭事件连接的是手机、APP，还是桥接层；后续 `error=-13` 不能独立证明最初原因。

## 最新修改中，需要优先核对的差异

首次成功版与当前版本同时存在几项差异，不能把失败完全归因于车机。

1. **USB 发送等待时间从 100ms 缩短到 20ms。** 两个版本都出现过超时，20ms 版也曾恢复发送，因此尚不能说缩短等待一定导致失败。但它直接影响当前失败的操作，应优先单独恢复到成功版参数做对照。
2. **已经处于配置 6 时，不再重新切配置。** 目的是减少重连时重置 USB 的影响，但也可能保留了上一轮异常状态。要对比“复用当前配置”和“只重新初始化网络接口”，不能直接认定复用必然更可靠。
3. **发送实现改为 native USB 调用。** 目的是避免旧 Android 同步 USB 调用对运行时的影响；当前调用仍超时。旧 Android 调用在上一版也有同类失败，所以 native 不是唯一可能原因，但需要在同样等待时间下单独对照。
4. **重新发起 CarPlay 的逻辑存在恢复盲区。** 当前代码要求“至少成功发送一个网络包”后才允许重发 `0x4301`。本轮发送成功数始终为零，这条恢复逻辑就始终不执行。若第一次启动请求未使手机网络通道就绪，该条件无法帮助恢复。代码关系可以确定，但“首次请求是否未生效”还需要实测。

因此，下一轮应保持同一数据线、500mA 通告、手机状态和媒体设置，一次只改变一项。先看小网络回应能否写出，再看 TCP 接入和首帧；避免同时改参数后无法分清原因。

## 卡顿的依据与处理顺序

统计首次成功期间 17:36:47—18:06:00 的日志，去除完全重复的行：

| 指标 | 实测值及含义 |
| --- | --- |
| 显示帧率 | 328 个统计窗口，中位数约 24fps |
| 视频解密 | 327 个窗口的平均耗时，中位数约 10.8ms；个别窗口记录单次峰值约 302ms |
| 解码管线 | 从送入解码器到取出输出，各窗口 p50 的中位数为 62ms，p90 的中位数约 126ms；不包含随后真正显示到屏幕的全部时间 |
| 触控 | 多个窗口的触控到画面平均耗时约 130—240ms；部分触控发送本身超过 100ms |

上述是日志窗口指标的统计，不是对所有视频帧重新计算的总体百分位数。解密、解码管线、触控发送的指标边界不同，不能直接相加。核对代码后，`touch2frame` 实际记录开始执行触控发送到下一份视频数据到达的时间，不包含触控执行队列之前的等待和随后真正显示到屏幕的全部时间，也不确认该帧必然对应这次操作。因此它只是响应延迟的诊断近似值，不能视作完整的实测触控到显示延迟。

这说明卡顿不能只归因于网络带宽：解密处理、显示管线和触控发送都有延迟迹象。还没有 CPU 采样证据，不能精确分配各部分责任。

原生加密实现已经加入，并通过车机上的标准向量及错误标签拒绝自检；但新版没有重新显示画面，**尚未测出实际性能收益**。本轮快照的 Java 堆使用约 12MB、上限 128MB，不能用它证明此前的内存不足已经修好，也不能证明运行画面时不存在内存增长。

代码上触控已经由专门的单线程队列发送，并非直接在界面线程执行网络写入。后续需要分别记录排队等待、事件写锁等待、加密和 socket 写入耗时；慢发送可能使后续触控排队，但当前计时尚未覆盖这部分。USB/lwIP 桥接由一个工作线程处理收发，同步发送超时时会延后该线程继续处理其他流量；它是需要测量的潜在放大因素，尚不能据此认定 lwIP 本身性能不足。

后续顺序应是：先稳定建立连接，再对比原生加密前后的耗时，然后单独尝试降低画面分辨率、调整显示输出，最后针对触控发送延迟检查桥接和排队。减少诊断日志也应作为独立对照，不能未经测量就认定它是主要瓶颈。

## 下一轮最短验证路线

1. 保留当前版本与报告，恢复成功版的 100ms USB 发送等待时间，先确认发送成功数是否能从 0 增长。
2. 若仍失败，同一等待时间下分别对照 Android/native 发送，以及网络接口重新初始化。每次记录实际配置、接口切换结果、发送耗时与错误码。
3. 增加有次数上限的启动恢复实验，避免恢复逻辑只依赖“已经成功发送”；确认它是否能让 USB 网络通道就绪，而不是无限重复启动请求。
4. 恢复首帧后，连续做多轮停止/启动和实际拔插；同时观察事件连接首次关闭的原因。软件停止/启动不能代替物理拔插验证。
5. 连接稳定后再比较解密、显示和触控延迟，确认优化是否真正改善操作感受。

**当前结论：lwIP 已经证明能够在这台车机上建立完整有线 CarPlay；重连恢复和操作流畅度仍未解决。本轮已把失败范围收敛到 USB 网络发送及其启动恢复过程，尚未查明最终根因。**
