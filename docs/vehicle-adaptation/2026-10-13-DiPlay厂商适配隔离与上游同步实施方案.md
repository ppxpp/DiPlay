# DiPlay 厂商适配隔离与上游同步实施方案

日期：2026-10-13。状态：实施规划，尚未实施。本方案补充《先锋车机 CarPlay 方控接管与本机播放器隔离方案》，不改变已确认的功能规则。

## 一、关键结论

**采用“集中适配包 + 通用接口 + 少量主线接入点”的方案。**第一阶段在现有 `shared`、`common` 模块内完成隔离，暂不拆出一组新的 Gradle 模块，也不批量迁移上游已有的吉利、比亚迪等实现。

本次新增的先锋代码、PAL 接入、QQ 音乐保护客户端、仪表协议以及现有先锋音频适配，都归入明确的适配边界。DiPlay 主线不再增加先锋类名、车机包名、PAL 按键数字、仪表消息编号或反射调用。

**隔离目标是减少并集中上游同步冲突，不能保证完全没有冲突。**音频输出和会话生命周期仍需要少量主线改动，因此必须记录接入位置、接口语义和验证方法。先隔离本次适配，后续有实际需要再升级为独立模块。

已确认的行为保持如下：

- CarPlay 实际会话连接即保护本机播放器，实际断开即解除；后台、暂停和导航间隙均保持保护，断开不主动恢复本机音乐。
- 方控切歌由 DiPlay 直接接入 PAL，再发送给 iPhone。音量由车机系统处理，同时保护本机播放器，覆盖音量操作导致的播放唤醒。
- 仪表歌曲信息优先验证 DiPlay 直连 CEAM 系统接口；成功后直接发布，不能直连时使用已分析的固定服务转发方案。
- 方控和仪表直连不等于阻止本机播放；播放器保护必须独立实现和验收。

## 二、代码边界

以下路径和名称均为规划，不代表当前已经存在这些文件。

| 位置 | 职责 | 依赖限制 |
| --- | --- | --- |
| `shared/.../vehicle/api/` | 会话状态、媒体命令、歌曲快照、音频策略及适配能力接口 | 不包含厂商名称、SDK 类型或 DiPlay UI 类型 |
| `shared/.../vehicle/runtime/` | 适配选择、连接期间保护、事件分发、歌曲发布和资源释放 | 依赖通用接口，通过回调使用 DiPlay 能力 |
| `shared/.../vehicle/adapters/pioneer/` | 先锋识别、PAL 输入、CEAM 仪表、先锋音频实现 | 依赖接口和必要的厂商 API，不访问 Activity 或主线内部状态 |
| `shared/.../vehicle/adapters/wecarflow/` | QQ 音乐保护 IPC、固定仪表服务协议兼容 | 与先锋输入和仪表直连接口分开，可按能力组合 |
| `common/.../vehicle/DiPlayVehicleIntegration.kt` | 将 DiPlay 会话、媒体发送和歌曲信息接到适配运行层 | 唯一应用层装配入口，不承载厂商协议 |

`...` 对应现有基础包路径 `src/main/java/com/shilapi/xcertplay`。保持 `common → shared` 的现有依赖方向，不新增 `shared → common` 依赖。

通用概念沿用 `MediaControlCoordinator`、`MediaCommand`、`SteeringWheelInputSource`、`LocalPlaybackGuardClient`、`AudioRouteController`、`NowPlayingPublisher` 和 `InstrumentMediaSink` 等名称。厂商名称只出现在具体实现，例如 `PioneerAudioRouteAdapter`、`PalSteeringWheelInputAdapter`、`CeamInstrumentMediaSink`。

车机厂商、输入协议、本机播放器与仪表输出是不同能力，不强行捆绑成一个“先锋所有权”对象。适配选择依据实际接口及设备特征，分别报告能力和当前状态，不能只凭品牌字符串全部启用。

选择集中包是为了先控制改动范围；包边界本身不是编译期隔离。通过依赖方向、集中装配和轻量检查约束边界。以后若 SDK 冲突、依赖体积或多厂商维护成本明显增加，再提取 `vehicle-api` 与厂商实现模块，主线接口尽量保持不变。

## 三、主线只保留四类接入点

| 接入点 | 主线负责 | 适配层负责 |
| --- | --- | --- |
| 会话生命周期 | 提供真实连接、断开及退出通知 | 建立和解除保护、监听与发布，处理重连和失效回调 |
| 媒体控制 | 提供向当前 CarPlay 会话发送语义媒体命令的入口 | PAL 事件解码、过滤、去重和有效会话检查 |
| 歌曲信息 | 在现有 NowPlaying 分发处提供只读快照 | 仪表协议转换、异步发送、进度更新与清除交接 |
| 音频输出 | 执行 AudioTrack 创建、焦点和写入等通用机制 | 提供厂商音频参数、源切换操作及保护就绪要求 |

主要需要检查的现有文件为 `CarPlayHostActivity.kt`、`CarPlayMediaKeys.kt`、`AndroidMediaSink.kt`；具体生命周期入口在实施时按真实回调确认。`CarPlayController` 的协议实现保持复用，不把厂商命令加入 CarPlay 协议层。

`CarPlayMediaKeys` 当前持有单个 `nowPlayingListener`，应在现有分发入口增加通知，不用新监听覆盖它。仪表调用异步执行，不阻塞媒体键锁或音频线程。PAL 命令使用明确的 CarPlay 目标，不能误走当前可能处理本地视频的路径。

迁移 `PioneerAudioRouting` 时，将厂商流号、Token、源号、反射和本机播放器操作移入适配实现；主线根据通用策略选择参数和写入方式。保留已经验证的媒体与导航焦点生命周期及非阻塞写入行为，不在迁移中重新设计整个播放器。

初始化一次适配选择和音频策略，避免 PCM 写入循环反复探测设备或调用 Binder。保护等待必须有界；建立失败时记录并明确降级，不无限卡住音频线程，也不宣称严格隔离已经成功。

## 四、实施顺序

1. **建立隔离骨架与主线接入清单。**新增通用接口、默认实现和集中装配入口。未匹配适配或关闭扩展时保留 DiPlay 原有路径；定义每个接入点的触发条件和线程要求。
2. **迁移已有先锋音频适配。**先搬厂商逻辑，再替换主线直接引用，保持现有出声行为。以先锋音乐、导航混音和断开重连验证没有引入倒退。
3. **接入保护与直接方控。**会话连接后立即建立本机保护，在可能唤醒本机播放器的音源激活前确认保护就绪；PAL 上下曲直发 iPhone，音量和 MODE 保留系统处理。QQ 音乐侧的保护修改在其项目独立维护，DiPlay 仅包含客户端和协议契约。
4. **验证并接入仪表直连。**先做 CEAM 歌曲文本最小实验，确认权限、显示、系统覆盖和退出交接，再接真实歌曲快照。若不成立，切换固定服务协议适配，不修改 DiPlay 包名冒充 QQ 音乐。
5. **整理维护边界与验收记录。**检查新增厂商代码是否全部集中、主线是否还有新增直接引用，并记录一次上游同步演练或下一次实际同步结果。

本次范围不包括重新组织所有已有厂商代码、迁移外置蓝牙代理或改变 iAP2/AirPlay 连接机制。这些功能继续按各自边界维护。

## 五、同步上游的维护方式

在 fork 内新增 `DiPlay/docs/厂商适配接入与上游同步说明.md`，集中记录四类接入点、适配选择、SDK 来源与必要版本、Manifest/AIDL/构建差异、默认行为和关键验证步骤。该说明是后续同步时的检查清单。

厂商 SDK、AIDL、混淆规则及服务声明尽量集中放置并记录来源；需要修改公共构建或 Manifest 时保持最小差异。不得把与适配无关的依赖升级、格式化或设置页重构混入适配提交。

实际实施时按“通用接入、音频迁移、方控与保护、仪表适配”分组提交。这样发生冲突或需要回退时，可以独立核对和恢复。当前工作区已有大量未提交改动，开始实施前先明确既有改动基线，不能将它们误当成本次适配提交。

同步上游时采用以下顺序：

1. 在独立同步分支合入上游更新，保留现有开发分支。
2. 优先按上游的新实现解决主线变化，再根据接入清单恢复必要的通用调用，不整段覆盖回旧文件。
3. 检查生命周期、NowPlaying 数据和音频参数语义是否改变；没有文本冲突也可能存在语义变化。
4. 构建受影响模块，检查未启用适配的默认路径，并进行先锋关键链路冒烟验证，再合入日常开发分支。

可以增加一条轻量边界检查：主线接入文件不得新增 PAL/CEAM SDK 引用或先锋实现引用；本机包名、源号和仪表消息号集中在适配目录。现有上游厂商引用作为既有范围处理，不借此强制全项目重构。

## 六、验收与尚待验证项

验收同时检查结构和实机行为：

- 新增厂商协议集中在适配目录；主线仅依赖通用接口，依赖方向无循环；关闭扩展后原有路径仍可用。
- CarPlay 连接、暂停、后台和仅导航期间，本机音乐均不播放；音量调节有效且不唤醒本机歌曲；切歌一次控制 iPhone 一次。
- 断开后解除保护，方控恢复本机行为，重连不累积监听或接收旧会话命令。
- 仪表切歌、暂停、进度和断开交接正确，不被本机旧信息持续覆盖；导航不伪造歌曲信息。
- 音乐和导航音频保持此前已验证的先锋路由行为；适配异常可诊断、可释放，不阻塞连接与音频工作线程。

目前 CEAM 直连调用权限及实屏显示仍需验证；PAL 客户端不能假定独占分发，解除监听能力也需确认。若不能解除监听，至少让旧回调失效，并确认重复注册的限制。若无法修改 QQ 音乐，需先证明系统层具有可靠的播放阻止能力，否则仅靠 DiPlay 接收方控和暂停指令不能达到严格保护要求。

本轮只形成方案并核对现有代码边界，未修改实现、构建或部署，未新增实机验证结论。
