# 2026年10月16日 22:38｜DiPlay与WeCarFlow冲突处理及弹窗说明

这份说明解释两件事：原来怎样避免两边一起响应音乐控制，以及本次新增提示弹窗如何工作。项目已经迁到本工作目录下，与DiPlay同级。

## 一、为什么两个应用会冲突

DiPlay负责把iPhone的CarPlay接到车机上；WeCarFlow是车机上的本地音乐应用。它们都可能收到方向盘上的播放、上一首、下一首操作。

如果两边同时响应，按一次下一首，可能既让iPhone切歌，又让WeCarFlow切歌或开始播放。车机切换音源、恢复之前的播放任务，也可能把WeCarFlow唤醒，造成两路声音争抢。

因此，现有策略是：**CarPlay连接期间，让iPhone负责音乐，WeCarFlow暂时停止本机音乐的播放和切歌。真正断开CarPlay后，再恢复WeCarFlow的正常使用。**

本次新增弹窗是为了把这个使用规则告诉用户。关闭弹窗只表示“我知道了”，不会取消保护，也不会授权WeCarFlow恢复播放。

## 二、目前双方怎样配合

### 1. CarPlay建立连接后，DiPlay通知WeCarFlow开启保护

双方通过Android提供的应用间通信机制联系。代码里的“Binder”和“保护服务”就是这条通知渠道，可以理解为DiPlay给WeCarFlow发出“现在由CarPlay接管音乐”的通知。

WeCarFlow收到通知后，先拦住新的本机播放请求，再清除已经排队但尚未执行的播放任务，并暂停正在运行的播放器。确认暂停检查成功后，才向DiPlay报告准备完成。

这里不是“USB线插着就认为连接了”，也不是“DiPlay窗口打开了就保护”。本次弹窗使用的依据是：**WeCarFlow已经收到活动连接的保护请求，播放拦截正在生效。**

如果DiPlay没有成功联系上这个改造版WeCarFlow，就不能保证完整保护已经建立。DiPlay现有逻辑会尝试暂停本机播放器，但仅暂停一次挡不住后续重新播放，因此不能当作完整保护。没有活动保护时，本次弹窗也不会假装保护已开启。

### 2. 方向盘按键：WeCarFlow让开，DiPlay处理

两边的分工如下：

| 操作 | DiPlay一侧 | WeCarFlow一侧 |
| --- | --- | --- |
| 方向盘播放切换、上一首、下一首 | 接收车机按键，并向iPhone发送对应CarPlay控制 | 保护期间，不再用这些操作启动或切换本机音乐 |
| 系统媒体播放和切歌请求 | 保持现有CarPlay控制通路 | 拦住会启动本机播放、改变本机曲目的相关入口 |
| 音量 | 沿用原车机音量处理 | 本补丁不通过静音或修改全局音量来隔离声音 |
| 显式暂停、停止等操作 | 沿用原有处理 | 相关原有暂停、停止路径保留，并非把全部媒体按键一律屏蔽 |

方向盘这条路径的重点是“避免两边同时动作”。不是WeCarFlow把每个方向盘事件再转发一次给DiPlay，避免因此造成重复切歌。

“PAL”是这台车机用于接收车辆按键的厂商接口名称。文档或日志里出现PAL，可以理解为“车机方控输入接口”。

### 3. 为什么不只拦方向盘按键

WeCarFlow还可能被页面上的播放按钮、系统媒体控制、自动恢复播放或稍晚才完成的加载任务唤醒。

原有改造同时检查了这些入口：播放请求、队列切歌、实际播放器启动，以及歌曲加载完成后自动播放的回调。保护期间阻止本机歌曲启动；连接前留下的旧任务，也不能在断开后突然自己开始播放。

可以把它理解为：既拦门口的新请求，也处理屋里已经排队的旧请求。保护不是仅靠一条“暂停”命令。

这不是对车机所有声音做全局静音，语音播报等不同用途的声音没有被一刀切封禁。

### 4. 仪表和桌面音乐信息尽量跟随CarPlay

连接期间，DiPlay把iPhone当前歌曲、歌手、播放状态和进度交给现有仪表显示通路；需要时也通过WeCarFlow原有的桌面/仪表服务传递，避免本机旧歌曲覆盖CarPlay信息。

这里与方向盘输入有所区别：通过WeCarFlow桌面服务收到的受支持播放、暂停、切歌操作，可以回传DiPlay，再由DiPlay交给iPhone。返回“受理成功”表示控制请求已接收，不等于手机已经执行完；显示状态仍以iPhone实际反馈为准。

实际仪表显示效果仍需在车机上检查，代码保留该通路不等于所有显示场景已经实测通过。

### 5. 哪些操作会解除保护

| 情况 | 保护是否继续 |
| --- | --- |
| CarPlay切到地图、没有播放音乐 | 继续 |
| CarPlay音乐暂停 | 继续 |
| DiPlay退到后台，但CarPlay连接还在 | 继续 |
| 用户打开WeCarFlow | 继续，同时按提示规则显示弹窗 |
| 用户关闭提示、勾选不再提示 | 继续 |
| CarPlay实际断开，DiPlay释放保护 | 解除 |
| 持有保护的DiPlay进程死亡，WeCarFlow收到断开通知 | 清理相应保护 |

保护解除后，WeCarFlow恢复本机功能和本机状态显示，**不会为了“恢复”而主动开始播放音乐**。用户可再自行选择播放。

## 三、本次弹窗如何使用

### 显示内容

标题：**CarPlay 音乐使用提示**

正文：

> CarPlay 已连接，方控按键冲突保护正在生效。
>
> 请使用 CarPlay 播放音乐，继续使用本应用播放音乐可能产生声音冲突。
>
> 关闭此提示不会关闭冲突保护。

下方提供“本次不再提示”复选框和“关闭”按钮。返回键也可以关闭；点击弹窗外部不会误关。

文案中的声音冲突是提醒用户遵守当前音源分工，不表示关闭提示就允许两边同时播放。WeCarFlow原有的播放拦截照常执行。

### 什么时候弹，什么时候不弹

| 使用情况 | 提示行为 |
| --- | --- |
| CarPlay没有连接，没有活动保护 | 不弹 |
| 保护生效时，用户打开WeCarFlow | 弹 |
| 上次停在歌单、搜索、播放页等其他页面，再回到应用 | 同样弹，不依赖首页 |
| 关闭提示后，在应用内部切换页面 | 不重复弹 |
| 没勾选“不再提示”，退到其他应用后再次打开WeCarFlow | 再弹一次 |
| 勾选“本次不再提示”后继续使用或反复打开应用 | 本次进程内都不再弹 |
| 勾选后CarPlay断开又重连 | 仍不弹；该选项直到WeCarFlow主进程重启才重置 |
| WeCarFlow主进程重启，随后保护再次建立 | 恢复正常提示规则 |
| 应用已打开，DiPlay稍后才重新建立保护 | 如本次尚未提示且未勾选免提示，补弹一次 |
| 弹窗显示时CarPlay断开、保护解除 | 关闭已经过期的提示 |

这里的“重启”指WeCarFlow主进程结束后重新启动。仅退到后台、再次点击图标，一般不算重启，因此勾选仍然有效。选项只记在内存里，不写入永久设置。

本次没有逐页修改界面，而是在应用统一的页面进入/退出入口处理。当前所有页面都在主进程，因此能覆盖现有页面；不需要额外申请悬浮窗权限。

### 仍需了解的既有边界

WeCarFlow如果整个主进程被系统结束，原有保护和本次免提示状态都会从内存消失。CarPlay仍连接时，需要DiPlay重新绑定并建立保护，之后提示才以新保护状态为准。已有逻辑支持重绑，但重绑前是否有短暂自动播放窗口仍需实测；本次没有用一个永久保存的“保护开启”开关将本机音乐一直锁住。

弹窗不会根据猜测补造“已连接”状态，因此也不能单靠弹窗消除这个既有边界。

## 六、建议的实车检查顺序

1. 未连接CarPlay，分别从首页和其他页面打开WeCarFlow：都不应弹。
2. CarPlay连接且保护建立后，从任意页面打开：应显示提示；关闭后，WeCarFlow仍不能因播放/切歌操作抢起本机音乐。
3. 未勾选免提示，切到其他应用再回来：应再提示；只在WeCarFlow内部切页：不应连续打扰。
4. 勾选免提示后，反复打开、切页、断开再重连CarPlay：都不应再提示，保护仍随实际连接正常开启/解除。
5. 真正重启WeCarFlow，让DiPlay重新建立保护：提示应恢复。
6. 最后检查方向盘上一首/下一首只控制CarPlay，没有双重切歌；音量、仪表歌名与实际声音也正常。

技术实现入口放在`wecarflow/patch-src/com/tencent/wecarflow/carplayguard/`，其中`GuardNotice`管理弹窗，`GuardNoticePolicy`只保存是否提示。原有保护规则详见`wecarflow/docs/runtime.md`和`wecarflow/docs/playback-hooks.md`。
