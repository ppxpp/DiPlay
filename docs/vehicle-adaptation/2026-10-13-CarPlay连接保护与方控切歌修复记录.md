# CarPlay 连接保护与方控切歌修复记录

## 关键结论

本轮针对用户实测的两项问题修改：连接后尚未播放时本机仍被唤醒，以及播放后方控无法切换 iPhone 歌曲。仪表同步用户已确认成功，本轮未调整该路径。未新增单元测试。

方控链路已定位到具体加载故障：DiPlay 未注册 PAL，而 QQ 日志仍收到 keyCode 8/9 并转向本机。DiPlay 缓存目录为空；提升诊断日志后确认 `PALServiceManager` 的 ClassNotFoundException，DexPathList 为 []。原因是 Android 7 的输入 DEX 和优化输出同目录，优化会覆盖或删除输入。分离目录后可加载 SDK 并绑定系统 PAL 服务，但进一步暴露 SDK 工作线程缺少 `com.google.gson.Gson`。现已补齐 Gson，并在 SDK 初始化前检查依赖。

连接保护代码也有明确缺口：客户端只等待首次绑定 1500ms，超时后服务即使晚到也不再申请保护；此前的重试仅在音频启动时触发。现已增加服务连接后的自动确认，不再依赖开始播放音乐。此外，QQ 端不能因为某个已有播放器暂停失败就撤销整个连接期间的保护，现改为保持播放拦截并单独记录暂停结果。

## 修改范围

- PAL 输入 DEX 放入 `files/vehicle-pal-sdk`，优化输出放入独立 code cache 目录。
- 提前准备 PAL SDK，输入命令仍受真实 CarPlay 会话状态约束。
- 补齐 SDK 必需的 Gson 依赖；记录 PAL 按键与 CarPlay 指令入队结果。
- QQ 保护服务迟到时自动开启保护；暂停检查失败不放开后续 PLAY/RESUME/NEXT。
- 保留已取消的签名、包名、UID 和 owner 校验状态。

## 快速验证结果与限制

DiPlay APK 构建成功，QQ 补丁 Java/d8 编译及完整 APK 重打成功。诊断版曾在车机确认两个加载故障及输入 DEX 修复后的 PAL 系统服务绑定；最终 Gson 修复包也已安装并启动。

随后车机从 ADB 断开，尚未采集到最终版本的 PAL 监听注册、物理上下曲成功或连接后不播放时的音量防唤醒证据。因此不能将编译和安装成功等同于两项实测问题已经全部解决。

本轮保留工作区其他代理、USB 和设置相关改动，只提交本次修复文件。Mac 防休眠进程已按用户要求停止。

## 手动测试

需要配套更新两个包：

- `artifacts/DiPlay-CarPlay-连接保护与切歌修复-20261013.apk`。
- `artifacts/QQ音乐-CarPlay-连接即保护修复-20261013.apk`。

先连接 CarPlay、不播放音乐，按音量和上下曲确认本机音乐不被唤醒；再播放 iPhone 音乐，按上下曲确认 iPhone 实际切歌，音量仍有效；最后暂停 iPhone 音乐再重复按键，确认保护持续存在。仪表歌曲信息应继续正常显示。
