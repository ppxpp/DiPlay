# WeCarFlow 音源恢复逻辑与 DiPlay 无声问题对照（2026-10-17 17:20）

## 先说结论

WeCarFlow 有一套“被系统打断后恢复”的处理，值得 DiPlay 借鉴。但它播放的是自己下载的音乐，DiPlay 播放的是 iPhone 发来的音乐；不能只复制恢复本机播放器的代码，就认为 CarPlay 会恢复声音。

目前无声问题还没有修复完成。已经确认，MODE 切换经过蓝牙音源后，iPhone 主动关闭了 CarPlay 音乐流。重新选择爱趣听音源并没有让这条流恢复。

## WeCarFlow 怎么做

“音频焦点”可以理解为车机授予应用的声音使用权。WeCarFlow 通过 PAL（腾讯车机与车厂之间的适配接口）申请和接收这一使用权的变化。

1. 失去使用权时暂停自己的播放器。
2. 单独记住这次暂停是用户自己点的，还是被系统打断。
3. 使用权恢复时，检查用户之前是否手动暂停；如果没有，恢复自己的播放。
4. 同时根据焦点变化激活或停用系统媒体会话，也就是车机用来识别播放器和分发媒体操作的登记。
5. 用户重新主动播放时，如果没有使用权，会重新申请。

## 与这次现场的区别

DiPlay 在音乐音轨创建时申请先锋媒体焦点（401）；音乐流关闭、音轨移除后，会撤销对应焦点请求。没有音轨时，后续旧焦点通知也不会被用于恢复播放。因此它缺少类似 WeCarFlow 的完整恢复链。

但这还不足以证明唯一根因：本次 iPhone 已经发送了关闭音乐流的 TEARDOWN 命令，除了恢复车机声音使用权，还必须让 iPhone 重新把音乐发送给 CarPlay。

## 已完成的实车对照

- 现场 Release v92：音乐界面和歌词继续，音乐数据停止；两个音频 UDP 入口被注销。
- Debug v93：物理 MODE 复现，明确记录 iPhone 关闭 100 类音乐流。
- Debug v94：单独 FM → 爱趣听，音乐数据持续，焦点能够恢复。
- Debug v94：单独“所有音源关闭 → 爱趣听”，音乐数据仍持续，没有重现同样的关闭音乐流现象。
- Debug v94：“下一个音源”从爱趣听进入蓝牙（205），约一秒后 iPhone 关闭音乐流，随后车机读到所有音源关闭（0）。这条路径复现了关键异常。
- 在故障连接内重新选择爱趣听（300），没有新的音乐流。
- 单独释放、申请再释放 CarPlay 音频资源，仍未观察到新的音乐流；申请资源还会让手机音乐暂停，因此不能把这个诊断动作直接用作自动修复。
