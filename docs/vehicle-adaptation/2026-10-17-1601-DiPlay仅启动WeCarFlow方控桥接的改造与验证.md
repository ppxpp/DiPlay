# 2026-10-17 16:01 DiPlay 仅启动 WeCarFlow 方控桥接的改造与验证

## 这次解决什么

车机重启后，WeCarFlow 没有运行，方向盘切歌键的兼容链路没有建立。用户要求 DiPlay 主动建立连接，但只启动需要的保护和方控逻辑，不能打开 WeCarFlow 主界面，也不能顺带启动音乐、恢复上次播放。

## 新方案的原理

把 WeCarFlow 中给 DiPlay 使用的代码放到一个单独的小进程，名字是 `com.tencent.wecarflow:carplayguard`。可以把它理解成 WeCarFlow 内的“方控转接员”，而不是打开整个音乐应用。

DiPlay 打开时先绑定这个转接员，建立服务关系，但不假装 CarPlay 已连接。真正连接 CarPlay 后才开启保护：阻止 WeCarFlow 播放，把转接员收到的前后曲命令传给 DiPlay，再交给 iPhone。CarPlay 实际断开时解除保护；应用切到后台不算断开。

这与“启动 WeCarFlow 后立即暂停”不同：新进程直接跳过原应用的业务初始化，不创建原播放器、不恢复歌曲，也不打开页面。

## 改动和兼容处理

- **独立启动**：保护服务和保护状态提供者移到专用进程。原主进程、核心进程在用户正常使用 WeCarFlow 时仍保留原初始化。
- **启动时预热**：DiPlay 主页面启动时绑定服务，CarPlay 连接时再握手获取保护。旧版服务仍在主进程时，拒绝通过它启动原应用，提示需要升级适配包。
- **方控监听**：专用进程只初始化 PAL 车机输入接口、订阅前后曲，不初始化播放器。PAL 是车机提供按键事件的接口。
- **防止一次切两首**：同一个实体按键可能同时从 DiPlay 直连和 WeCarFlow 桥接送达，用实体事件签名去重；不同按键事件仍可以快速连续触发。
- **跨进程保护**：已经运行的原主进程和核心进程主动登记 Binder。Binder 可以理解为进程之间保持的一条通信线路。保护端只调用已经登记的线路，不通过查找内容提供者去拉起原应用。
- **重连登记**：保护进程被回收后，仍在运行的原进程会重新绑定、登记。缺少必要登记时，不会虚报保护就绪。
- **提示与仪表**：原主进程已运行时，通过登记线路同步保护变化和歌曲信息，保留原有提示与仪表逻辑；不会为了显示提示或歌曲而启动原主进程。
- **升级支持**：DiPlay TCP 更新入口增加对 WeCarFlow 的支持，只允许本应用和 WeCarFlow 两个包名，并核对各自已安装版本的签名。不会卸载、清数据或更改其他应用。

- 已进行只读代码复核，修正了跨路径按键重复、误拉原进程风险、保护进程重启后登记丢失、提示跨进程同步等问题。

## 安装解析失败的调查

用户在安装 WeCarFlow 时遇到“包解析失败”。目前不能归因为 Android 版本不支持：最低版本、签名格式、APK ZIP 完整性检查均通过，TCP 服务在车机也曾成功读取该 APK 的包信息并确认签名。

安装交接发现两处风险：旧安装页仍可能使用的 APK 会被下一次传包删除；OEM 安装器对内容 URI 的转交也需要明确的读取授权。v91 改为保留近期上传文件，并通过 MIME、ClipData 与显式 URI 授权交给安装器。新的上传响应会返回车机收到文件的 SHA-256，供本地核对。

这是正在验证的修正，不能在安装成功前认定已证明解析失败的唯一原因。

## 尚待真车确认

1. v91 安装后重新传 WeCarFlow，摘要一致且系统完成覆盖安装。
2. 只启动 DiPlay，确认 WeCarFlow 仅运行 `:carplayguard`，没有原主进程或播放器进程被连带启动。
3. PAL 状态为 registered；CarPlay 连接后保护 guarded/ready 均为 true。
4. 实际方向盘前后曲有效，按一次只切一首；WeCarFlow 不在后台自行播放。
5. 实际车机重启、保护进程回收和 CarPlay 断开后的恢复。

不通过 TCP 擅自清除应用数据，也不把“服务绑定成功”当作物理方控已经验证通过。
