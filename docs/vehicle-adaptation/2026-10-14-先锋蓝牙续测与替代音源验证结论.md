# 先锋蓝牙续测与替代音源实机验证结论

日期：2026-10-14。设备：先锋 SABRESD_MX6DQ，Android 7.1.2 / API 25。仅做目标模块构建、覆盖升级和实机技术验证，未运行单元测试、全量回归或 lint。电脑在执行期间通过 `caffeinate -dimsu` 保持唤醒。

## 结论

1. **直接先锋蓝牙路径本轮仍未打通。**普通 UID 可以查询 SDK 和 IOSMgr、注册回调，但三次 IOSMgr 65 连接请求均返回 `-109`，没有形成 SPP / iAP2 字节通道。改成 `com.tencent.wecarflow` 没有解决该连接错误。不能据此认定硬件不支持 CarPlay、SSP 不合格或 MFi 不可用。
2. **固件存在 iPod、USB、AUX 和应用音源 301，但当前都不能切入。**状态均为 `MEDIASTATUS_INVALID=2`，实际 `change2Source(1, id)` 均返回 `-1`。没有验证到一个能直接代替媒体 300、承载 CarPlay 音乐的独立主音源。
3. **改用 FRONT 11、DIXIM 241 或 REAR 12 不等于换了主音源。**这些是音轨流 / 输出总线；本轮实验仍使用媒体 300。FRONT 11 显式设置 `com.tencent.wecarflow.media` 可以消费 PCM，但仍借用同一音乐音源。导航 400 进入 MIX，可与 FM 并存，属于此前已有的导航路径。
4. **不能通过简单换通道删除现有的原生播放器协调。**当前验证可激活并消费 PCM 的主媒体路径仍为媒体 300、FRONT 和媒体令牌。需要保留先锋路由、焦点及令牌处理；若原生音乐播放器同时存在，暂停、方控和播放权协调仍须处理。本轮没有修改原生播放器 APK，也没有完成实际车内听感验证。
5. **包名会显著影响音轨映射。**固件硬编码将 `com.tencent.wecarflow` 的 AudioTrack 改成厂商媒体流 401，因此该包名下请求标准流 3 也会实际进入 FRONT 11；不能用这个结果宣称普通应用的标准 Android 音频路径已可用。

## 蓝牙续测

测试身份：`com.tencent.wecarflow`，UID 10092，普通应用，无 root。

| 检查 | 实测结果 |
| --- | --- |
| 先锋适配器 | 开启，`isBtValid=true`，`getSppEnableApple=true`，`isSppConnectable=true` |
| iPhone profile | 支持掩码 143，连接掩码 3，配置掩码 3；SDK 配置只有 HFP 107 与 A2DP 108 |
| IOSMgr 71 | HFP=1 |
| IOSMgr 67 / 79 | SPP=0、设备状态=0；dumpsys BT 槽 invalid |
| IOSMgr 74 | 上次结果=1，仍不是当前已连接的证据 |
| IOSMgr 77 | 回调注册成功，status=0 |
| IOSMgr 65 | 08:35:23、08:39:18、08:50:54 三次均为 `-109`；服务端也记录 `call IAP Error = -109` |
| 回调 / 字节 | 未观察到 IIOSClient 字节事件 87，没有可供协议引擎使用的真实 stream |
| IOSMgr 78 | 实验后注销成功，status=0；65 未受理，未发送断开 66 |

当前故障发生在系统 SPP / iAP 连接入口，尚未进入应用 iAP2 协议协商。原配置未选串口目标与静态分析中的“无目标时返回 -109”相符，但本轮没有证明是哪一个内部目标条件缺失。未盲改成 SPP_APP、HOMESERVER，也未接管系统 iAP 客户端。EIR/SDP、SSP 加密属性、MFi 和 Wi-Fi 协商仍未验证；小米代理链路的历史成功不算作这条直接蓝牙路径的成功。

## 其它主音源

| 音源 | ID | 状态 | 实际切换 | 判断 |
| --- | ---: | --- | --- | --- |
| USB | 202 | INVALID 2 | -1，仍为原音源 0 | 当前不可用，不能作为独立 CarPlay 入口 |
| iPod | 203 | INVALID 2 | -1，仍为 0 | 存在原生 iPod 客户端，但 IOSMgr 无设备 / 会话；蓝牙配对没有使它变为有效音源 |
| AUX | 204 | INVALID 2 | -1，仍为 0 | 当前不可用；配置标记为 MCU 管理的外部输入，不是新增的 Android PCM 总线 |
| TAI_APP | 301 | INVALID 2 | -1，仍为 0 | 无对应活动 source client，当前没有可用的第三方应用主音源 |
| 媒体 | 300 | VALID 3 | 0，回读 300 | MainToken 为 `com.tencent.wecarflow.media`；401 焦点获准 |
| FM 对照 | 201 | 有效 | 0，回读 201 | MainToken 为 `mediamanager.source.name.fm` |

设备 `/system/etc/mediamanager.conf` 的前排列表为 tuner、aux1、usb1、btaudio、OFF-SOURCE，另外定义原生 ipod1。配置中 `<app>` 列表为空。MediaController 中出现常量、source client 注册存在，都不能代替“当前有效、能切入”的证据。这里没有排除插入真实 USB / iPod 设备后原生音源变为有效的可能，但也没有证明它们能被 DiPlay 独立用作任意 PCM 输入。即便以后借用成功，仍需验证对应令牌、播放权、原生 USB / iPod 播放器和按键行为。

## 排除包名干扰后的通道对照

先确认车机原有 `com.tencent.mm` 也是 ProbeActivity 测试包，再覆盖升级作对照，UID 保持 10091。最终版本 4 的完整采样如下；播放头数值仅证明数据消费，不表示已确认扬声器声音。

| 测试身份 / 请求 | 实际 legacy type / 总线 | 音源与令牌 | 约 4 秒末播放头 |
| --- | --- | --- | ---: |
| mm：标准流 3 | 2 / SPEAKER | 媒体 300，音轨默认 STREAM_UNKNOW | 0；32768 字节填满，341 次零写入 |
| mm：FRONT 11，显式媒体 token | 11 / FRONT | 媒体 300、媒体 token | 171872 |
| mm：DIXIM_FRONT 241 | 11 / FRONT | 仍为媒体 300，音轨默认 STREAM_UNKNOW | 172583；不能用消费进度证明未知 token 获得声音出口 |
| mm：REAR 12，显式媒体 token | 12 / REAR | 仍为媒体 300、媒体 token | 173900；没有形成另一个可选主音源，也未确认前排扬声器听感 |
| mm：导航 400，焦点 400 | 10 / MIX | FM 主音源 + `com.autonavi.amapauto` 混音 token | 173544；混音焦点获准 |
| mm：媒体 401，焦点 401 | 11 / FRONT | 媒体 300、媒体 token | 167427；媒体焦点获准 |
| wecarflow：标准流 3 | 被固件改为 11 / FRONT | 媒体 300、媒体 token | 168387 |

从实际框架 AudioTrack 构造器确认了包名分支：`com.tencent.wecarflow` 强制构造 legacy stream 401；其它包名重新映射传入的 contentType。本轮 mm 请求标准流 3 后，实际 legacy type 为 2，普通 SPEAKER 输出再次出现写入阻塞。这不是一条可替代的通用音乐出口。

明确区分：**音源 ID 203 不是 AudioTrack stream 203；FRONT 11 / REAR 12 也不是可以代替主音源 300 的新播放器音源。**本轮观察到的音频策略输出仍为 SPEAKER、MIX、FRONT、REAR，没有独立名为 iPod、USB 或 AUX 的 Android AudioTrack 输出总线。

本轮车机上的 `com.tencent.wecarflow` 在开始排查前就已经是测试 APK，因此没有真正原生 QQ 音乐与探针同时播放的现场条件。实验可以说明原生音乐程序不必负责解码这些 PCM，却不能证明恢复原生播放器后不再需要暂停或方控协调。本轮也没有通过这个包名再部署 DiPlay 主程序。

## 部署、清理和证据

- 增加音源 / 流清单、低幅度 440Hz PCM 验证、ADB 启动动作、实际 stream 记录和实验后恢复音源；改动仅在 `DiPlay/bluetooth-probe`。
- 两个已有测试身份均通过 `adb install -r -t` 升级到版本 4，没有卸载重装，UID 不变。版本 3 的属性诊断误用了固件缺少的 `getAudioAttributes()`，曾导致探针崩溃；已改为兼容读取，版本 4 表格中的七次实验均有完整 PCM FINAL 和清理记录，版本 3 失败采样不用于通道结论。私有属性反射在本固件返回不可读，最终映射采用 `getStreamType()`、框架与 AudioFlinger 的一致证据。
- 每次 PCM 实验调用 stop / release、释放本次焦点并恢复原音源 0；最后停止对照包，主探针保留可继续使用。IOSMgr 回调已注销，电话和音乐 profile 配置未修改。普通 SPEAKER 输出复现的服务端阻塞 / 残留轨道保存在最终快照中，未通过重启音频服务或车机清除；FRONT / MIX / REAR 的实验音轨已结束。
- 主探针 APK（本地产物：`artifacts/CarPlay-Bluetooth-Audio-Probe-20261014.apk`，不提交 Git）：SHA-256 `8c3421f77c3de37b69189ecbd2b7b8b5fd0984a426a76c4a057eea4811884f64`。
- 对照探针 APK（本地产物：`artifacts/CarPlay-Audio-Control-Probe-20261014.apk`，不提交 Git）：SHA-256 `2efc705f2fa387d84a68b9a89e48f668c9ce7a3badf52c7e3b6858b763c0d8c8`。
- 实际安装 APK 已拉回，与以上本地产物逐一核对 SHA-256。
- 私有证据：`DiPlay/.private/validation/2026-10-14-bt-audio/`。包含蓝牙报告、完整 logcat、源管理 / AudioFlinger / policy 快照、实际系统配置、安装校验、构建日志和 `v4-matrix.json`。`run-matrix.py` 是本轮 ADB 实机采样脚本，不是单元测试。

要进一步摆脱原生媒体 300，需要证实一个真正独立且可激活的主音源，以及它的 PCM 输入、令牌和控制契约；本轮没有找到这样的入口。当前可据实使用的方案仍是媒体 300 的先锋适配，而不是简单选择 iPod。
