# DiPlay 中的 A 设备管理需求

日期：2026-10-11｜状态：需求整理稿｜范围：需求与功能边界，不是实施计划

## 1. 目标与已确认约束

在 Android B 的 DiPlay 中增加“A 设备管理”页面。用户通过 B 完成外置 A 的首次配置、
日常管理、故障查看和软件升级。最终 A 是无屏专用硬件，正常使用只需供电；当前 Android
手机代理只是验证载体，其前台页面、系统设置及 ADB 配置不能成为最终产品的使用步骤。

- A 负责与 iPhone 的蓝牙连接及原始字节透传，不承担 MFi 认证、视频解码或音视频转发。
- B 负责 iAP2、认证、AirPlay/CarPlay、音视频及触控，也是主要管理入口。
- 不在 B 预置 A 的 IP，也不要求用户手工查看 IP；在每次连接时发现当前地址。
- 最终 A 长、宽均不超过 20 mm；厚度及外壳/天线边界待确认，开发阶段 Android 手机不受此限制。
- A 必须支持 5 GHz Wi-Fi，配网与网络管理须覆盖 5 GHz；仅有 2.4 GHz 的完整 A 不符合要求。
- A 保存配置，上电后自动联网、发布服务并准备接受 B 的连接；断网或掉电后可恢复运行。
- 管理能力不依赖 A 的屏幕、电脑、USB、厂商调试工具或云服务。
- 面向专用硬件定义管理能力；Android 验证端通过适配实现同一功能语义。
- 先验证必要的操作闭环，不因这一需求默认增加详细开发计划或全量测试。

此前提到的 iPhone 操作仍可作为辅助入口，但本稿以 B 的原生 DiPlay 页面为主。
iPhone 浏览器能否覆盖全部管理功能，列为待确认范围，不视为本轮已要求的完整第二套界面。

## 2. 当前已有能力与缺口

| 项目 | 当前情况 | 管理需求 |
|---|---|---|
| A/B 自动发现 | NSD 与 UDP 发现；B 已有“A 设备”查找、绑定与解除入口 | 扩展多设备选择与管理状态 |
| 配对凭据 | B 输入 A 配对码并验证保存，旧 debug 配置自动迁移 | 专用硬件通过标签或首次配置入口提供授权依据 |
| 状态与日志 | A 页面和本地日志，B 有 CarPlay 日志 | B 统一呈现 A 状态，支持远程获取日志 |
| 启动代理 | 打开 A 应用后自动启动前台服务，退出页面持续运行 | 系统开机/上电自动运行，B 管理启动、停止及恢复 |
| 网络配置 | 通过 Android 系统设置 | 无屏 A 必须具备手机可访问的首次配网与恢复入口 |
| 软件升级 | 开发工具安装 APK | 能力查询、升级操作、结果与失败恢复；硬件支持 OTA |
| 完整链路 | 已验证路由器下发现、认证与画面 | 管理操作不能干扰正常 CarPlay 数据链路 |

Android 手机上的验证结果只代表原型，不代表 ESP32 或双芯片固件已经具备相同能力。

## 3. 用户使用流程

### 3.1 首次使用

1. A 上电；未配置时进入可识别的配置状态。
2. 用户在 DiPlay 打开“A 设备管理”，选择“添加设备”。
3. 通过设备提供的首次配置入口识别 A、建立管理授权并配置目标 Wi-Fi。
4. A 加入目标网络；B 自动重新发现并确认是同一台 A，完成绑定。
5. 在 B 查看可用的 iPhone、配对状态并选择目标手机；需要 iOS 授权时提示用户在 iPhone 操作。
6. 保存默认目标和自动运行设置；确认 A 无需本地点击即可进入可用状态。

**首次配网不能只依靠 mDNS。** A 尚未进入 B 的网络时无法使用当前同网发现流程。
需要单独的配置通道；临时配置热点加手机配网为候选方案，BLE 配网为另一候选。
在确认硬件与平台能力前，不将任一候选写成已实现功能。
手机因配网暂时离开原网络时，页面须引导返回并自动续接流程。

首次添加必须有设备持有者可获得的授权依据，例如设备标签上的一次性配对信息，
不能让同网任意设备自动取得 A 的管理权；最终选择的方式须满足 A 无屏、无操作按键的约束。

### 3.2 日常使用

A 上电并自动联网；B 自动发现已绑定 A，建立授权管理连接并按 DiPlay 的连接设置启动 CarPlay。
用户无需每次进入管理页。管理页关闭或退到后台，不应停止代理或中断 CarPlay。

### 3.3 更换网络、设备或 iPhone

- 改网络：先提交新配置，再确认 A 已在新网络出现；失败时有可再次访问的恢复配网入口。
- 换 A：明确选择新设备、建立授权，不因发现同名服务自动替换原绑定。
- 换 B：支持授权新 B 或转移管理权；同一时刻只允许一个 B 控制实际透传会话。
- 换 iPhone：在 B 选择新目标，明确提示配对、遗忘旧配对或切换目标对当前会话的影响。
- A 恢复出厂设置：清除网络、管理授权与 iPhone 绑定；B 显示需要重新配置。

恢复出厂设置既要有已授权管理操作，也要有无法联网、无法登录时的无屏恢复办法；
具体办法待硬件能力确认，不能只提供一个离线时不可访问的按钮。

## 4. 页面功能

建议入口为 DiPlay“连接”分类中的“A 设备管理”。管理页包含概览、设备与连接、网络、
运行日志、软件升级。日志详情可单独展开，首页只显示当前故障及必要摘要。

### 4.1 设备与状态概览

| 信息 | 需求 |
|---|---|
| 设备身份 | 名称、稳定设备 ID、设备型号、硬件版本 |
| 软件情况 | 软件/固件版本、管理协议版本、支持的管理能力 |
| 运行情况 | 在线状态、运行时长、最近一次启动/重启原因（支持时提供） |
| 网络情况 | 当前网络名称、地址、信号质量、最后一次成功通信时间 |
| B 连接 | 管理连接与透传连接分别显示；是否被其他 B 占用 |
| iPhone 连接 | 目标名称、配对、蓝牙连接、RFCOMM 连接状态 |
| 透传情况 | 当前阶段、双向字节计数、当前会话标识、最近结束原因 |
| CarPlay 情况 | B 自己报告的认证、AirPlay、画面与音频状态；不得伪称来自 A |
| 错误 | 可理解的原因、发生时间及下一步建议；保留技术详情供展开查看 |

未知、暂不可读、不支持与故障要分别呈现。失联后显示“离线/状态已过期”和最后更新时间，
不能持续把缓存中的“已连接”作为当前状态。设备 IP 可作为诊断信息查看，但不要求用户配置。
内存、温度、芯片运行指标仅在设备提供时展示，不要求 Android 和所有硬件均具备。

### 4.2 连接管理

- 发现、添加、绑定、解除绑定 A；名称重名时以稳定设备 ID 区分。
- 查看 A 上已有的 iPhone 配对，扫描/选择目标、进入蓝牙可配对状态及遗忘配对（按能力提供）。
- 启动、停止代理；查看结果而非仅显示“命令已发送”。
- 发起完整 CarPlay 重连：由 B 协调当前会话关闭与 A 的 bootstrap，不能只重启 A 的 TCP 服务。
- 重启 A、恢复网络配置和恢复出厂设置；影响当前使用或清除配置的操作需明确确认。
- 提供自动运行、默认 iPhone 等必要设置；保存后由 A 保持，不依赖 B 持续在线。
- 其他 B 已占用会话时显示原因；不无提示抢占、断开现有用户。

“停止代理”与“断开 CarPlay”是不同操作。页面应说明实际影响，并使用 B 的会话控制
完成用户明确请求的 CarPlay 断开。只打开管理页、刷新日志或关闭页面不得触发重连。

### 4.3 网络管理

- 查看已连接网络及已保存配置，配置、替换或移除 Wi-Fi；密码默认隐藏。
- 覆盖同一路由器和 B 热点两类使用方式；不把当前小米的热点配置当成所有设备的默认值。
- 配网失败、密码错误、网络不可达、服务发现失败要区分显示。
- B 热点或路由器 IP 变化后自动重新发现 A，不需要编辑地址。
- 改网络时明确提示可能临时断开管理连接与 CarPlay；支持重现设备或恢复配置状态。
- 必须解决“改错网络后无法再管理 A”的恢复路径，而非无限重试错误配置。

### 4.4 运行日志

- 查看实时或增量日志，支持暂停滚动、按级别/连接阶段筛选与导出。
- 每条日志包含来源、会话、阶段、事件与时间；A 时钟未校准时用运行时间并由 B 补接收时间。
- 保留最近错误与断线原因；同一会话能关联 B 的认证、AirPlay 和 CarPlay 日志。
- A 使用有容量上限的日志缓冲；断线后支持补取尚在缓冲中的日志并提示缺失区间。
- 默认不记录令牌、Wi-Fi 密码、认证私钥及原始协议载荷；导出诊断包也需脱敏。
- 日志读取不能堵塞蓝牙透传；大量日志可降频或丢弃非关键记录，并显示丢弃计数。
- 支持清理日志；设备不支持落盘时说明重启后日志可能不可恢复。

### 4.5 软件升级

- 查看当前版本、硬件型号、升级能力及可用版本信息；不能仅显示一个没有后端的升级按钮。
- 区分“升级 DiPlay B”和“升级外置 A”，下载/选包、校验、上传、安装与结果分别显示。
- 支持本地升级包；在线升级来源及发布渠道待确认，不将联网作为唯一升级方式。
- A 校验设备型号、硬件版本、升级包真实性和兼容性；不接受错误板型或截断包。
- 开始安装前协调停止受影响的会话，明确提示暂时不可用；避免未经用户同意自动升级。
- 展示进度、重启等待、重新发现和升级后的实际版本；上传完成不等于升级成功。
- 上传中断允许重试；安装失败或启动失败应可恢复，硬件支持时回滚到可运行版本。
- 双芯片 A 需要展示各组件版本；升级包声明组件兼容关系和更新顺序，不能只升级其中一个
  导致整机不可运行。原型阶段允许只实现单组件，但不得表示双芯片升级已完成。
- Android 验证端采用 APK 安装适配，专用硬件采用固件升级适配；权限、安装确认与回滚
  能力分别验证。Android 端需要本机交互的限制不能延续为最终无屏硬件的正常流程。
- 不支持升级的设备返回明确能力与原因，UI 显示当前限制；不伪造升级成功。

## 5. 连接状态的正确含义

需要分别维护以下状态，不以一个“已连接”代替全部链路：

1. A 系统：未配置、启动、运行、升级、重启、故障。
2. A 网络：未连接、正在连接、已联网、断网。
3. B 管理通道：发现、授权、在线、过期/离线。
4. A/B 透传：待命、打开 RFCOMM、透传、正常移交完成、异常结束。
5. A/iPhone：未配对、已配对、蓝牙/RFCOMM 连接中、已连接或故障。
6. B/CarPlay：iAP2、认证、网络引导、AirPlay、运行、断开或失败。

**Wi-Fi iAP2 接管后 RFCOMM 正常关闭是已验证流程。** 此时页面应显示
“CarPlay 运行，蓝牙引导已完成”，不能显示“蓝牙断开，连接失败”。
管理通道独立于透传会话，正常移交后仍须能查询 A、日志及版本。
A 后续离线时，若 B 与 iPhone 的 CarPlay 仍正常，应同时显示这两项事实。

## 6. A/B 管理协议要求

本节定义双方职责，不提前确定 HTTP、WebSocket 或具体接口路径。

- 管理通道与 CPBT 原始字节透传分开；管理状态和日志不能混入 iAP2 字节流。
- A 宣告稳定设备 ID、管理能力/协议版本及当前管理端点；具体 IP 动态发现。
- 不依赖 Android 包名、Activity、ADB、文件路径或某一芯片实现，B 的业务页面保持平台无关。
- 支持能力协商：Android 原型、单芯片和双芯片硬件只提供各自真实可用功能。
- 发现广播不泄露凭据；发现名称、蓝牙地址和 mDNS TXT 本身不是管理授权依据。
- 除受限首次配置入口外，管理命令、日志和升级均需授权；密码、令牌与升级通信须保护。
- 返回可识别的错误及请求/操作 ID，长操作有进度和最终结果；网络超时不能判定操作未执行。
- 请求重试不能重复重启、清除配置或安装；重连后能够查询未完成操作的状态。
- 定义占用、授权失败、版本不兼容、发现超时、网络丢失、配对拒绝和升级失败等结果。
- 管理页仅在需要时拉取详细数据；通信中断时退避重试，不因查询频率影响 CarPlay。

## 7. 优先级与验证范围

| 优先级 | 必需能力 | 最小验证闭环 |
|---|---|---|
| 首轮管理验证 | B 页面、设备发现/身份/授权、状态、日志、版本/能力、启动停止与重连 | 在 B 管理 Android A，能够关联真实连接过程和错误 |
| 无屏使用必需 | 手机首次配网/绑定、iPhone 配对处理、上电运行、断线恢复、换网恢复 | 新 A 只供电，不访问 A 屏幕或用 ADB 即可完成配置与运行 |
| 软件升级必需 | 选包、校验、执行、进度、重新发现、版本确认与失败恢复 | 完成一次真实升级和一次可恢复失败；按目标平台验证 |
| 后续增强 | iPhone 辅助网页、更多运行指标、多设备体验、在线版本源 | 不阻塞必要管理闭环，按实际需要增加 |

以上是需求优先级，不表示“无屏使用”和升级已经实现，也不以 Android 页面操作
代替硬件闭环。无需为本稿展开排期、全量回归或详细开发计划。

## 8. 待确认的产品选择

1. iPhone 是否需要提供完整独立管理能力，还是只负责蓝牙/CarPlay 授权及辅助配网？
2. A 的首次配网与持有者授权方式：临时热点、BLE 或其他方式；无网络故障如何恢复？
3. 软件升级先验证 Android APK，还是优先定义硬件 OTA；本地包之外是否需要在线发布源？
4. 设备绑定策略：默认一 A 对一 B，是否允许多 B 授权并进行明确的会话转移？
5. 专用硬件的实际组成和资源条件，用于确认蓝牙配对确认、自动启动、组件升级和回滚能力。

默认建议：一个活动 B 控制会话，B 原生页面为主要入口，本地升级包先行。
其他未确认选择不应被隐藏为实现中的固定假设。

## 9. 验收要点

- 新设备无需预置 IP；完成一次用户可操作的添加/授权后可被 B 自动发现和连接。
- 管理页能解释 A 当前状态和最近故障，不把正常蓝牙移交误报为 CarPlay 失败。
- 在 B 查看和导出 A 日志；日志操作不影响 CarPlay 画面、声音及触控。
- 关闭管理页后仍正常运行；A/B 换 IP、短暂断网或 A 断电重启后能重新发现和恢复。
- 最终硬件只供电即可日常工作；首次配置、必要授权及故障恢复通过手机完成。
- 升级显示真实结果，错误包被拒绝，断电/失败后有已验证的恢复路径。
- Android 原型与硬件已验证/未验证能力明确区分，不以界面存在代替功能完成。
